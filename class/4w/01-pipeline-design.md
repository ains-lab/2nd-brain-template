# 4주차 — SNS 키워드 수집 파이프라인 설계

> 대상: Meta **Threads**, X, Reddit. 여기서 thread는 일반 댓글 스레드가 아니라 Threads 서비스를 뜻한다.
> 작성·자료 확인: 2026-09-22. 교육 자료이며 플랫폼 전체를 빠짐없이 수집하는 상용 서비스가 아니다.

## 1. 무엇을 만들 것인가

사용자가 등록한 검색어로 공개 게시물을 주기적으로 검색하고, 응답 스냅샷과 분석용 테이블을 분리해 저장한다. 이후 Hermes에서 SQL 집계, 주제 분류, 기사 링크 분석에 활용한다. 실습 스냅샷은 비밀정보 유출을 줄이기 위해 허용 필드만 정규화한 JSON이며, HTTP 응답 원본의 byte-exact 보관본은 아니다.

**권장 원칙: 수집은 결정론적 코드, 해석은 Hermes/OMH.** 매 시간 LLM에게 “웹에서 찾아서 저장해”라고만 시키면 검색 범위·중복·실패 기록이 실행마다 달라질 수 있다.

```text
사용자 → keywords.json (플랫폼별 검색식·안정적인 query_id)
                      │
Hermes gateway → cron (--no-agent)
                      │
               Python 수집기
                ┌─────┼─────┐
                X   Threads Reddit   ← 각 플랫폼에서 승인된 API
                └─────┼─────┘
                      ↓
        응답 캡처 + SQLite + 실행 상태
                      ↓
            JSONL / SQL 집계 / 품질 점검
                      ↓
       Hermes + OMH: 코드 검토·분석·근거 있는 보고서
                      ↓
        사람이 검토한 결과만 선택적으로 Wiki에 승격
```

| 구성요소 | 책임 | 하지 않는 일 |
| --- | --- | --- |
| Hermes | 도구 실행, cron 등록, gateway, 후속 분석 | SNS 접근 권한 자동 발급 |
| OMH | Hermes 위의 작업 오케스트레이션·검증 지원 | 세 SNS의 무제한 데이터 API 제공 |
| Python 수집기 | HTTP 요청, 정규화, 저장, 중복 제거, 오류 상태 | 게시물 속 지시문 실행 |
| SQLite | 분석 가능한 로컬 데이터와 실행 기록 | 원본의 진실성·대표성 보장 |
| 사용자 | 키워드·예산·접근 권한·보존 정책 결정 | 토큰을 채팅에 붙여 넣을 필요 없음 |

OMH가 꼭 매번 수집 루프에 들어가야 하는 것은 아니다. OMH로 수집기와 분석 과정을 설계·개선하고, 승인한 코드를 cron으로 반복 실행하는 것이 안정적이다.

## 2. 플랫폼별로 다른 검색 계약

| 플랫폼 | 기본 실습의 수집 대상 | 인증·운영 관문 | 분석 시 주의 |
| --- | --- | --- | --- |
| X | Recent Search의 공개 게시물 | 개발자 프로젝트·토큰·검색 API 이용 자격과 과금 확인 | recent 검색은 전체 과거 기록이 아님 |
| Threads | Keyword Search의 공개 게시물 | Threads 앱·사용자 토큰·키워드 검색 권한 | 사용 가능한 검색 범위와 필드는 Meta 문서 및 앱 상태에 의존 |
| Reddit | 검색 결과의 submission/link 게시물 | 승인된 Data API 이용, OAuth, 식별 가능한 User-Agent | 댓글 검색·댓글 전체 수집과는 별개 |

공개 웹페이지가 보인다는 사실만으로 자동 수집 허가가 생기지는 않는다. API가 403을 반환하면 권한·승인 문제를 해결한다. 쿠키 탈취, 프록시 회전, 로그인 우회 또는 CAPTCHA 우회로 대체하지 않는다.

## 3. 검색어는 문자열 하나보다 “관리 대상”이다

예를 들어 연구 관심이 `AI agent security`라면 다음처럼 **플랫폼마다 별도 검색식**을 둔다.

- X: `"AI agent" security -is:retweet`
- Threads: `AI agent security` — X 연산자가 동일하게 동작한다고 가정하지 않는다.
- Reddit: `"AI agent" AND security` — subreddit 제한은 별도 실험 후 추가한다.

`id`는 검색 정의의 식별자다. 같은 의미를 유지하며 실행할 때는 유지하고, 검색식·언어·범위를 바꾸면 `agent-security-x-v2`처럼 새 ID를 사용한다. 여러 검색어에 같은 글이 걸려도 **글 테이블은 한 건**, 검색 일치 관계는 여러 건이어야 한다.

키워드 확장은 처음부터 LLM에 맡겨 무제한으로 하지 않는다. 사람이 승인한 동의어 목록·변경 이유·적용일을 기록한다. 키워드가 바뀌면 수집량 증가가 실제 유행인지 검색 조건 변화인지 구분해야 한다.

## 4. 데이터 계층과 최소 필드

| 계층 | 목적 | 핵심 내용 |
| --- | --- | --- |
| API 응답 스냅샷 | 보존 필드 재처리·추적 | 정규화된 응답 데이터, 수집 시각, 검색 ID; 토큰과 인증 헤더 제외 |
| 게시물 테이블 | 중복 없는 분석 | `(platform, id)`, URL, 원문, 작성 시각, 관측 시각, 지표 |
| 검색 매칭 테이블 | 키워드별 분석 | 검색 ID와 게시물의 다대다 관계 |
| 실행 상태 테이블 | 관측 품질 | 성공/부분 수집/실패, 건수, 오류 분류 |
| 파생 결과 | 분석·보고 | SQL 집계, 분류 모델 버전, 해석, 근거 URL |

`created_at`은 글이 작성된 때, `collected_at`은 수집기가 본 때다. UTC로 저장하고 보고서에서 Asia/Seoul로 표시한다. 글이 수정되거나 좋아요가 늘어날 수 있으므로 수집 시각 없이 참여 지표를 비교하지 않는다.

수집 응답의 재현성을 위해 평소에는 캡처 파일을 덮어쓰지 않는다. 단, 이것이 영구 보존 허가를 뜻하지는 않는다. 플랫폼 삭제·보존 요구가 있으면 원본 캡처, DB, 내보내기, 백업까지 삭제하는 절차가 우선이다.

예제 DB의 게시물은 최초 관측을 유지한다. 이후 본문 수정·참여 지표 변화는 실행별 스냅샷에서 확인해야 하며, DB의 지표를 현재 최신값이라고 부르면 안 된다. Threads 예제는 외부 링크 필드를 요청하지 않아 `external_urls`가 비어 있다. X의 URL entities와 Reddit의 URL만 구조화하며, Threads 기사 링크 분석에는 허용 필드 추가 또는 원문 링크 추출 단계가 필요하다.

## 5. 게시물과 기사는 다른 데이터다

기본 실습은 **SNS 게시물·게시물 안의 링크**를 모은다. 링크된 언론 기사 전문을 자동으로 수집하는 구현은 포함하지 않는다.

기사까지 필요하다면 다음을 별도 단계로 설계한다.

1. 게시물의 외부 URL을 후보로 추출한다. `post_url`과 `article_url`을 분리한다.
2. 동일 URL·리디렉션·추적 파라미터를 검토해 기사 후보를 중복 제거한다. 서로 다른 기사를 과도하게 합치지 않는다.
3. 허용된 발행사 API/RSS, 라이선스 또는 명시적으로 허용된 웹 접근으로 메타데이터와 허용 범위의 본문을 받는다.
4. 유료벽·로그인 우회는 하지 않고 `metadata_only`, `blocked`, `not_fetched`를 기록한다.
5. 기사 하나를 공유한 게시물 여러 개를 별도 관계 테이블로 연결한다.

기사 URL이 있는 글을 “기사 내용까지 확보한 글”로 집계하면 안 된다. SNS 링크 수와 고유 기사 수, 본문 확보 기사 수를 각각 보고한다.

## 6. 실습 MVP와 운영 시스템의 경계

실습은 적은 키워드를 대상으로 **최신 검색 결과를 제한된 페이지 수만큼 반복 조회하는 방식**이다. 완전한 증분 수집기나 전체 기록 백필 시스템은 아니다. 다음 페이지가 남았는데 한도에 도달하면 성공이 아니라 `partial`로 표시해야 한다.

운영 확장 시 필요한 항목:

- 플랫폼·검색어별 체크포인트와 검색 조건 버전. 모든 페이지 처리 및 DB 커밋 성공 후에만 진행 위치 확정.
- 조회 구간을 약간 겹쳐 늦게 검색에 등장한 글을 재확인하고 ID로 중복 제거.
- 실패한 구간을 재처리하는 큐. 플랫폼의 과거 검색 허용 기간보다 오래 멈추면 복구 불가능한 공백 표시.
- 중복 실행 방지, 실행 시간 제한, 요청/일 예산 상한, 토큰 만료·갱신 관리.
- 각 검색별 마지막 성공 시각, `partial` 비율, 401/403/429, 수집량 급감 경보.
- 삭제·보존 요청 처리 및 백업 암호화. 개인정보는 필요한 최소 범위만 저장.

**“검색 성공 0건”과 “인증 실패라서 0건”은 전혀 다르다.** 또한 최근 조회가 성공해도 API 검색 인덱스에 빠진 글이나 조회 상한 바깥 글까지 없었다는 의미는 아니다.

## 7. 이 저장소의 Wiki와 분리

`class/4w/`는 강의 문서와 코드이지 canonical Wiki가 아니다. 실습 DB와 캡처는 저장소 바깥의 개인 데이터 폴더에 둔다. 이 작업은 `SCHEMA.md`, `index.md`, 기존 `raw/` 또는 canonical 페이지를 수정하지 않는다.

추후 Wiki에 넣으려면 원본 Markdown 캡처 → `SCHEMA.md`에 따른 provenance·해시 → canonical 정리 → index/log 동기화 순으로 별도 승인·검증한다. JSONL이나 DB를 현재 Wiki의 `sources`로 바로 적지 않는다.
