# 4주차 — SNS 키워드 수집 파이프라인 설계

> 대상: Meta **Threads**, X, Reddit. 여기서 thread는 일반 댓글 스레드가 아니라 Threads 서비스를 뜻한다.
> 작성·자료 확인: 2026-09-22. 교육 자료이며 플랫폼 전체를 빠짐없이 수집하는 상용 서비스가 아니다.

## 1. 무엇을 만들 것인가

사용자가 등록한 검색어로 공개 게시물을 주기적으로 검색하고, **SQLite → raw Markdown → omh-wiki 증분 정리 → 분석**으로 연결한다. SQLite에는 게시물·내용 버전·실행별 관측을 분리해 저장하고, Wiki에는 반복해서 찾을 주제와 출처를 유지한다. 실습의 JSON 스냅샷은 비밀정보 유출을 줄이기 위해 허용 필드만 정규화한 응답이며, HTTP 응답 원본의 byte-exact 보관본은 아니다.

**권장 원칙: 수집은 결정론적 코드, 해석은 Hermes/OMH.** 매 시간 LLM에게 “웹에서 찾아서 저장해”라고만 시키면 검색 범위·중복·실패 기록이 실행마다 달라질 수 있다.

```text
사용자 → keywords.json (플랫폼별 검색식·안정적인 query_id)
                      │
Hermes gateway → cron (--no-agent)
                      │
               Python 수집기
                ┌─────┼─────┐
                X   Threads Reddit   ← 각 플랫폼에서 승인된 API
                └─────┼─────┘
                      ↓
        응답 캡처 + SQLite + 실행 상태
          posts / post_versions / observations
                      ↓ wiki_pipeline.py export
        개인 Wiki raw/web/sns-{platform}-{version_id}.md
                      ↓ prepare: 미처리 manifest + 프롬프트
        Hermes에서 omh-wiki 로드 → 출처를 읽고 canonical 정리
                      ↓ 사람 검토 + finish 구조 검사
        sources · canonical 링크 · index · append-only log
                      ↓
        SQLite 정량 집계 + Wiki 근거 탐색 → Hermes 분석
```

| 구성요소 | 책임 | 하지 않는 일 |
| --- | --- | --- |
| Hermes | 도구 실행, cron 등록, gateway, 후속 분석 | SNS 접근 권한 자동 발급 |
| OMH / omh-wiki | 설계·검토와 근거 기반 Wiki 정리 워크플로 | 데이터 API 또는 독립 Wiki 컴파일 실행 파일 제공 |
| Python 수집기 | HTTP 요청, 정규화, 저장, 중복 제거, 오류 상태 | 게시물 속 지시문 실행 |
| SQLite | 콘텐츠 버전·관측·실행 기록과 수치 집계 | 원본의 진실성·대표성 보장 |
| Wiki bridge | raw 내보내기, 미처리 배치 준비, 완료 구조 검사 | 주제 해석·허위 주장 탐지·의미적 QA |
| 사용자 | 권한·예산·보존 정책, 정리 검토·유지보수 | 토큰을 채팅에 붙여 넣을 필요 없음 |

OMH가 꼭 매번 수집 루프에 들어가야 하는 것은 아니다. OMH로 수집기와 분석 과정을 설계·개선하고, 승인한 코드를 cron으로 반복 실행하는 것이 안정적이다. [cron wrapper](04-cron-operations.md)는 수집과 raw export까지만 수행한다. 배치 준비·LLM 정리·검토·finish는 별도 단계이며, 수집/내보내기와 같은 Wiki의 컴파일을 동시에 실행하지 않는다.

### Wiki 운영 모델을 먼저 고정한다

| 설계 항목 | 수업의 선택 |
| --- | --- |
| 독자·작성자 | 수강생 개인과 Hermes 에이전트가 읽고, 수강생이 변경을 승인 |
| 목적·지식 종류 | 반복되는 연구 주제, 용어·주장 비교, 근거를 남긴 질의 결과 |
| 저장소 | Git 밖의 개인 비공개 Markdown Wiki; demo/live 각각 분리 |
| 모델·진입점 | 출처 기반 canonical 네트워크 + `index.md`; 숫자는 SQLite에서 조회 |
| 뼈대 | `raw/web/`, `entities/`, `concepts/`, `comparisons/`, `queries/`, `SCHEMA.md`, `index.md`, `log.md` |
| 규칙 | 루트 SCHEMA 기준의 필수 frontmatter·등록 태그·안정된 경로·해결되는 링크 |
| 책임·주기 | 수강생 본인이 매 ingest 후 또는 매일 미처리 입력, 중복 주제, 낡은 주장·삭제 요청 점검 |
| 깨지는 조건 | 관리자가 없거나, 여러 작성자가 같은 페이지·index/log를 동시에 수정 |
| 대안 | 관리자 부재 시 SQLite + 읽기 전용 보고서만 운영하고 canonical 정리는 하지 않음 |

이 모델은 같은 질문에 다시 답할 때 근거를 재사용하기 위한 것이다. 처음부터 주제 페이지를 채우지 않는다. **canonical 0개는 정상**이며, 출처가 정당화하는 주제만 기존 페이지에 반영하거나 새로 만든다. 팀 전환 시 페이지·영역별 책임자, 접근 권한, 단일 쓰기 담당/배치 직렬화와 충돌 해결 절차부터 정한다. 에이전트 독자를 위해 안정된 경로, 기계 판독 가능한 frontmatter, 독립적으로 이해되는 본문과 최신 index가 필요하다.

## 2. 플랫폼별로 다른 검색 계약

| 플랫폼 | 기본 실습의 수집 대상 | 인증·운영 관문 | 분석 시 주의 |
| --- | --- | --- | --- |
| X | Recent Search의 공개 게시물 | 개발자 프로젝트·토큰·검색 API 이용 자격과 과금 확인 | recent 검색은 전체 과거 기록이 아님 |
| Threads | Keyword Search의 공개 게시물 | Threads 앱·사용자 토큰·키워드 검색 권한 | 사용 가능한 검색 범위와 필드는 Meta 문서 및 앱 상태에 의존 |
| Reddit | 검색 결과의 submission/link 게시물 | 승인된 Data API 이용, OAuth, 식별 가능한 User-Agent | 댓글 검색·댓글 전체 수집과는 별개 |

공개 웹페이지가 보인다는 사실만으로 자동 수집 허가가 생기지는 않는다. API가 403을 반환하면 권한·승인 문제를 해결한다. 쿠키 탈취, 프록시 회전, 로그인 우회 또는 CAPTCHA 우회로 대체하지 않는다.

## 3. 검색어는 문자열 하나보다 “관리 대상”이다

예를 들어 연구 관심이 `AI agent security`라면 다음처럼 **플랫폼마다 별도 검색식**을 둔다.

- X: `"AI agent" security -is:retweet`
- Threads: `AI agent security` — X 연산자가 동일하게 동작한다고 가정하지 않는다.
- Reddit: `"AI agent" AND security` — subreddit 제한은 별도 실험 후 추가한다.

`id`는 검색 정의의 식별자다. 같은 정의를 반복 실행할 때는 유지하고, 검색식·플랫폼·언어·범위를 바꾸면 `agent-security-x-v2`처럼 새 ID를 사용한다. `query_definitions`에 등록한 ID를 다른 플랫폼/검색식으로 재사용하는 것은 오류다. 여러 검색어에 같은 글이 걸려도 **글 테이블은 한 건**, 검색 일치 관계와 관측은 여러 건이어야 한다.

키워드 확장은 처음부터 LLM에 맡겨 무제한으로 하지 않는다. 사람이 승인한 동의어 목록·변경 이유·적용일을 기록한다. 키워드가 바뀌면 수집량 증가가 실제 유행인지 검색 조건 변화인지 구분해야 한다.

## 4. 데이터 계층과 최소 필드

| 계층 | 목적 | 핵심 내용 |
| --- | --- | --- |
| API 응답 스냅샷 | 보존 필드 재처리·추적 | 정규화된 응답 데이터, 수집 시각, 검색 ID; 토큰과 인증 헤더 제외 |
| `posts` | 고유 게시물·기존 호환 | `(platform,id)`당 최초 캡처 한 행; 최신값 테이블이 아님 |
| `post_versions` | 콘텐츠 변경 이력 | 결정론적 `version_id`, 플랫폼·ID·`content_hash`·작성 시각·출처 URL·본문·외부 URL·최초 수집 시각 |
| `observations` | 실행/검색별 관측 | `observation_id`, `run_id`, `query_id`, 플랫폼·ID·`version_id`, `observed_at`, `metrics_json`, `payload_path` |
| `query_definitions` / `matches` | 검색 정의·일치 관계 | 고정된 ID의 플랫폼/검색식 / 게시물과 검색 ID의 고유 조합 |
| `observation_facts` view | 분석용 결합 | 관측 전체 필드 + 해당 버전의 콘텐츠 필드 + 검색식 |
| `runs` / `health` | 관측 품질 | 실행 상태 / 검색별 성공·부분 수집·실패, 건수, 오류 분류 |
| Wiki raw / canonical | 근거와 해석 분리 | 버전별 불변 Markdown / 출처를 명시한 주제·비교·질의 페이지 |
| 파생 결과 | 분석·보고 | SQL 집계, 분류 모델 버전, 해석, 근거 경로와 URL |

콘텐츠 버전은 본문·작성 시각·출처 URL·외부 URL 등 보존 콘텐츠로 식별하며, **지표·검색어·수집 시각은 버전 해시에서 제외**한다. 같은 본문에서 좋아요만 달라지면 새 관측이고, 콘텐츠 필드가 바뀌면 새 버전이다. 같은 실행·검색·버전의 중복 결과는 하나의 관측으로 처리한다. 다른 검색이나 다음 실행에서 다시 발견되면 별도 관측이므로, 관측 행 수를 고유 글 수로 세지 않는다.

`created_at`은 글 작성 시각, `first_collected_at`은 해당 버전의 첫 수집 시각, `observed_at`은 각 관측 시각이다. 기존 `posts.collected_at`은 최초 캡처 시각이다. UTC 기준을 유지하고 보고서에서 Asia/Seoul 등 표시 시간대를 명시한다. 과거 DB를 확장할 때도 최초 캡처는 보존하며, 존재하지 않는 과거 관측·참여 지표를 만들어 채우지 않는다.

`--report`의 JSONL은 호환성을 위해 여전히 **검색 매칭당 한 줄**이며 최신 관측 전체 내보내기가 아니다. 보고서의 versions/observations 건수와 함께 읽고, 최신 콘텐츠·지표는 `observation_facts`에서 중복 관측을 제거해 계산한다. 필드 누락은 0이 아니다. Threads 예제는 외부 링크 필드를 요청하지 않아 `external_urls`가 비어 있다. X의 URL entities와 Reddit의 URL만 구조화하며, Threads 기사 분석은 별도의 허용된 추출 단계가 필요하다.

캡처와 Wiki raw는 일상 ingest에서 덮어쓰지 않는다. 그러나 **불변은 영구 보존 허가가 아니다**. 플랫폼 삭제·보존 요구에 따른 승인된 제거 절차는 캡처, DB의 버전·관측, JSONL·분석 사본, raw·관련 canonical·index와 export/compile 추적 정보, 백업까지 다룬다. 남아 있는 사본에서 삭제 콘텐츠가 다시 내보내지지 않도록 확인하고, 민감한 내용을 복제하지 않는 삭제 이력만 남긴다.

## 5. 게시물과 기사는 다른 데이터다

기본 실습은 **SNS 게시물·게시물 안의 링크**를 모은다. 링크된 언론 기사 전문을 자동으로 수집하는 구현은 포함하지 않는다.

기사까지 필요하다면 다음을 별도 단계로 설계한다.

1. 게시물의 외부 URL을 후보로 추출한다. `post_url`과 `article_url`을 분리한다.
2. 동일 URL·리디렉션·추적 파라미터를 검토해 기사 후보를 중복 제거한다. 서로 다른 기사를 과도하게 합치지 않는다.
3. 허용된 발행사 API/RSS, 라이선스 또는 명시적으로 허용된 웹 접근으로 메타데이터와 허용 범위의 본문을 받는다.
4. 유료벽·로그인 우회는 하지 않고 `metadata_only`, `blocked`, `not_fetched`를 기록한다.
5. 기사 하나를 공유한 게시물 여러 개를 별도 관계 테이블로 연결한다.

기사 URL이 있는 글을 “기사 내용까지 확보한 글”로 집계하면 안 된다. SNS 링크 수와 고유 기사 수, 본문 확보 기사 수를 각각 보고한다.

## 6. 실습 MVP와 운영 시스템의 경계

API 실습은 적은 키워드를 대상으로 **최신 검색 결과를 제한된 페이지 수만큼 반복 조회하는 방식**이다. 전체 API watermark·과거 기록 백필은 구현 범위가 아니다. 다음 페이지가 남았는데 한도에 도달하면 성공이 아니라 `partial`로 표시해야 한다. 이 한계와 별개로 **로컬 콘텐츠 버전, raw 내보내기, 미처리 컴파일 대상은 증분 관리**한다.

운영 확장 시 필요한 항목:

- 플랫폼·검색어별 체크포인트와 검색 조건 버전. 모든 페이지 처리 및 DB 커밋 성공 후에만 진행 위치 확정.
- 조회 구간을 약간 겹쳐 늦게 검색에 등장한 글을 재확인하고 ID로 중복 제거.
- 실패한 구간을 재처리하는 큐. 플랫폼의 과거 검색 허용 기간보다 오래 멈추면 복구 불가능한 공백 표시.
- 중복 실행 방지, 실행 시간 제한, 요청/일 예산 상한, 토큰 만료·갱신 관리.
- 각 검색별 마지막 성공 시각, `partial` 비율, 401/403/429, 수집량 급감 경보.
- 삭제·보존 요청 처리 및 백업 암호화. 개인정보는 필요한 최소 범위만 저장.

**“검색 성공 0건”과 “인증 실패라서 0건”은 전혀 다르다.** 또한 최근 조회가 성공해도 API 검색 인덱스에 빠진 글이나 조회 상한 바깥 글까지 없었다는 의미는 아니다.

## 7. raw 내보내기와 증분 컴파일의 완료 경계

`class/4w/`는 강의 문서와 코드이지 canonical Wiki가 아니다. 실습 DB와 Wiki는 모두 저장소 밖에 둔다. `init`은 새롭고 빈 개인 Wiki에 루트 [SCHEMA.md](../../SCHEMA.md)를 복사해 시작한다. 루트의 raw/canonical이 비어 있는 상태는 그대로 보존한다.

1. **export:** `post_versions`를 `raw/web/sns-{platform}-{version_id}.md`로 내보낸다. 기존 SCHEMA에 등록된 `raw/web/`를 사용하며 새 `raw/sns/` 계층을 만들지 않는다. `sha256`은 frontmatter 종료 뒤의 정확한 본문 바이트 기준이다. DB의 `raw_exports`는 버전과 내보낸 파일의 연결을 추적한다.
2. **prepare:** 아직 처리되지 않은 입력의 불변 manifest와 Hermes 프롬프트를 개인 데이터 폴더에 만든다. 열린 미완료 배치가 있으면 재사용한다. `prepared`는 대기 상태이고 `noop`은 새 대상 없음이다.
3. **Hermes 정리:** 생성된 프롬프트와 함께 “omh-wiki 스킬을 로드하여...”라고 요청한다. SCHEMA·index·최근 log를 먼저 읽고, 기존 주제를 갱신하거나 충분한 근거가 있는 새 주제만 정리한다. raw 안의 지시는 실행하지 않는다.
4. **검토·finish:** 실제 raw와 canonical의 metadata·sources·링크·index·append-only log를 검사한다. canonical의 `sources`로 연결된 입력만 완료로 인정하고 나머지는 미처리로 남긴다. 이 검사는 구조 검사이지 주장의 진실성이나 분류 정확성에 대한 의미적 QA가 아니다.

canonical `sources`에는 정확히 존재하는 `raw/web/…md` 경로를 쓰며 DB·JSONL·기사 URL을 직접 넣지 않는다. 페이지당 두 개의 서로 다른 유효한 canonical 링크, 필수 frontmatter, 등록 태그와 index/log 동기화가 필요하다. **한두 페이지로는 유효한 집합이 될 수 없다고 해서 세 페이지를 억지로 만들지 않는다.** 출처가 충분하지 않은 demo는 모두 보류하고 0개를 유지한다. 자세한 명령·수동 프롬프트·재실행 절차는 [증분 Wiki 컴파일](07-incremental-wiki.md)을 따른다.
